# Протокол оценки

## Данные и область проверки

`tests/eval/data/documents.json` содержит четыре синтетических документа по восемь
страниц. `cases.jsonl` — 48 одиночных вопросов; `dialogues.json` — четыре двухходовых
диалога. Документы и вопросы созданы совместно. Разметка не прошла независимую экспертизу.

| Набор | Документы | Одиночные вопросы | Диалоги |
|---|---|---:|---:|
| dev | Атлас: мастерская; Орион: регистратор | 16 ответимых, 8 неответимых | 2 × 2 хода |
| test | Лира: API; Кедр: библиотечный пилот | 16 ответимых, 8 неответимых | 2 × 2 хода |

Dev используется для настройки. Документы test не пересекаются с dev, но доступны
разработчику: это открытая регрессионная проверка, а не слепой внешний holdout.
Пороги gate выбраны на dev. Промпт уточнён после разбора первоначальных ответов dev;
вопросы, разметка, retrieval и пороги при этом не менялись. Итоговый test выполнен
после фиксации промпта. По его результатам параметры не подбирались.

PDF генерируются одним способом и проходят настоящий парсер, очистку и чанкинг.
Проверка не покрывает разнообразие вёрстки, OCR и сложные таблицы. При текущих
параметрах в каждом документе восемь чанков: top-6 охватывает до 75% документа.
Для проверки масштаба и обобщения нужен другой, существенно больший корпус.

## Доказательства

Положительный случай содержит эталон ответа и группы `evidence`. Для полного ответа
нужны все группы; внутри группы можно указать альтернативные цитаты. Каждая цитата
имеет физический номер страницы PDF, начиная с 1, и дословный текст.

Сравнение нормализует Unicode NFKC, регистр и пробелы. Зачёт требует полного вхождения
цитаты в один чанк с подходящим диапазоном страниц. Попадания только на нужную страницу
недостаточно. Разделённая между чанками цитата не склеивается: это консервативное
ограничение метрики. Альтернативная правильная формулировка без разметки тоже может
не получить зачёт.

Для вопросов без ответа записано объяснение: отсутствует цена, запрошен другой период,
перепутаны температура хранения и рабочая температура и т. п. Отсутствие ответа
проверяется по полному документу. Валидатор JSON не доказывает правильность такой разметки.

Перед прогоном проверяются схема, ID, дубликаты вопросов, split документа и присутствие
цитат в исходном тексте. Oracle recall проверяет, сохранились ли доказательства среди
всех чанков после извлечения и разбиения. Потерянный при обработке случай остаётся
в знаменателе итоговой метрики.

## Поиск

Для ответимых вопросов рассчитываются метрики при k = 1, 3, 6:

| Метрика | Определение |
|---|---|
| Hit@k | Есть хотя бы одно доказательство |
| Evidence recall@k | Найденная доля необходимых групп доказательств |
| Complete@k | Найдены все необходимые группы |
| Precision@k | Доля возвращённых чанков с доказательством; знаменатель — фактически возвращённое число |
| MRR@6 | Обратный ранг первого доказательства среди первых шести; ранг 7 получает 0 |

Пустой результат даёт 0. MRR измеряет первое попадание и не заменяет полноту составного
ответа. В JSON сохранены значения каждого вопроса, средние по вопросам без взвешивания
по числу доказательств (`question_mean`), средние по документам (`document_macro`)
и разбивки по тегам. Теги пересекаются; их счётчики нельзя суммировать.

Dense, BM25, RRF и включённый по отдельной конфигурации reranker получают одинаковые
чанки, вопросы, разметку и итоговые k. `HybridRetriever.rank` используется и приложением,
и eval. Hybrid объединяет два списка до 20 кандидатов и имеет больший вычислительный
бюджет, чем отдельный поиск. Это сравнение конфигураций, не сравнение при равном compute.

Время поиска — общий проход всех включённых ранжирований после одного прогрева на
документ. Загрузка весов и индексация в него не входят. Это не отдельная латентность
каждого метода и не нагрузочный тест.

Неответимые вопросы не включаются в retrieval recall/MRR. На двух документах в наборе
доверительные интервалы и статистическая значимость не публикуются. Вопросы внутри
одного документа зависимы; разница одного случая не доказывает преимущество метода.

## Gate

Gate применяется к выбранному контексту. В отчёте отдельно записаны:

- ложные отказы / число ответимых вопросов;
- ложные пропуски / число неответимых вопросов, с разбивкой по типу отрицательного примера;
- число пропущенных ответимых вопросов с неполным контекстом.

Калибровка разрешена только на dev с реальными эмбеддингами. Цель — минимум среднего
из доли ложных отказов и доли ложных пропусков, то есть balanced error. Сетка cosine:
0.55, 0.60, 0.65, 0.70, 0.72, 0.75, 0.80, 0.85, 0.90; coverage: 0.25, 0.50, 0.75, 1.0.
При равенстве выбираются меньшие FN, cosine, coverage в этом порядке. Полная сетка
сохраняется. Исходные 0.72 / 0.5 дали выбор 0.8 / 0.5; компромисс описан в результатах.

```bash
uv run python -m tests.eval.run_eval --split dev --calibrate \
  --config docs/evaluation/baseline-config.json --output artifacts/eval/calibration.md
uv run python -m tests.eval.run_eval --split test \
  --config artifacts/eval/calibration.calibrated.json
```

Параметры из eval не переносятся в приложение автоматически. Тематическая близость
не доказывает наличие ответа; gate не заменяет проверку отказа итоговой модели.

## Полный прогон

`--with-llm` вызывает настоящий `RagService`: уточнение вопроса, поиск, gate, промпт,
провайдер и сохранение истории. Каждый одиночный вопрос начинает с пустой истории.
В диалоге второй ход использует фактический первый ответ, эталон не подставляется.
При ошибке хода следующие ходы этого диалога не выполняются. Переписанный запрос
с цифровыми значениями, которых нет в вопросах пользователя, отклоняется. Запасной
запрос содержит текущий и предыдущий пользовательские вопросы; это ограниченная
защита от выдуманных уточнений, не проверка всех сущностей.

Предикция содержит исходный вопрос, фактический поисковый запрос, найденный контекст,
выданные источники, ответ, признак gate-отказа, время первого текста, полное время и
ошибку. Время первого текста включает retrieval и при необходимости уточнение;
шаблон gate-отказа не является временем генерации LLM.

Пустой ответ, ошибка провайдера, обрыв потока и остановка по лимиту токенов не считаются
успехом или правильным отказом. Неполный прогон сохраняет ошибки, получает
`complete=false` и завершает CLI ненулевым кодом. Семантические баллы для него
не публикуются.

Наличие цитаты, допустимый номер страницы и точное совпадение с шаблоном отказа —
диагностика формата. Они не доказывают правильность ответа. В частности, отказ
другими словами может быть корректным, а число из эталона — встречаться в неверном утверждении.

## Рубрика разбора ответов

Проверяющий читает вопрос, эталон, полный документ, переданный контекст и ответ.
Для каждого случая заполняются пять полей:

| Поле | Критерий true |
|---|---|
| correctness | Нет ошибочных фактов, отрицаний, версий, единиц и вычислений |
| completeness | Ответ покрывает все ответимые части; неизвестные сведения явно обозначены |
| faithfulness | Утверждения подтверждены переданным контекстом; вычисления воспроизводимы |
| refusal_appropriate | Наличие или отсутствие отказа соответствует полному документу |
| citation_support | Все содержательные утверждения имеют ссылки, которые их подтверждают |

`answer_mode`: `answer`, `partial`, `refusal`. Для чистого правильного отказа первые
четыре поля могут быть true, `citation_support=null`. Ответ без необходимых ссылок
получает false. Ложный отказ на ответимый вопрос получает false по correctness,
completeness и refusal_appropriate; если утверждается отсутствие сведений вопреки
контексту, также false по faithfulness. Отсутствие ответа из-за gate не исключает
такой случай из оценки конечного результата.

Нужны ID проверяющего, `reviewer_type` (`human` или `assistant`) и объяснение со ссылкой
на доказательства. Run ID и хэш предикции связывают оценку с конкретным ответом.
Пустые оценки, дубликаты, пропуски и подмена предикции отклоняются. Итоги публикуются
с числителями и знаменателями отдельно для одиночных вопросов и диалогов, ответимых
и неответимых случаев. Единого «quality score» нет.

В текущем отчёте разбор выполнен Codex по этой рубрике: это оценка ассистентом,
не независимая человеческая экспертиза. Для внешних выводов нужны независимые
проверяющие, исходные оценки и разрешение разногласий. Итоги одного ассистента
не измеряют межэкспертное согласие.

```bash
uv run python -m tests.eval.review --run artifacts/eval/my-run.json \
  --reviews artifacts/eval/my-run.review.jsonl \
  --output artifacts/eval/my-run.review-summary.json
```

## Воспроизведение

```bash
make test
make lint
make eval-bm25
make eval-smoke
make eval
make eval-test
make eval-llm
```

`tests/eval/config.json` фиксирует retrieval, ревизии E5/reranker, CPU, температуру
и лимит генерации. Retrieval-настройки `.env` игнорируются. Только с `--with-llm`
провайдер, его адрес, имя модели и ключ читаются из окружения. Ключи и URL в отчёты
не попадают.

Для текущей LLM использованы LM Studio, Ministral 3 3B Instruct Q4_K_M, контекст
8192 и один запрос за раз. Имя файла и SHA-256 указаны в `evaluation/runtime.json`.
Температура 0 уменьшает вариативность, но не гарантирует повторяемость API.
Основной отчёт содержит один итоговый прогон на каждом наборе; выбор лучшего из
нескольких итоговых ответов не выполнялся.

У каждого запуска отдельный run ID. JSON содержит полную конфигурацию, промпты,
версии пакетов, платформу, хэши кода, датасета, lockfile и извлечённого текста,
все чанки и ранжирования. PDF-хэш не используется как стабильный идентификатор:
служебные метаданные генератора могут меняться.

Отчёты сохраняются под уникальными именами в `artifacts/eval/`. Явно заданные
существующие файлы не перезаписываются. Отобранные отчёты и их сырые данные лежат
в `docs/evaluation/`; временные прогоны исключены из Git.
